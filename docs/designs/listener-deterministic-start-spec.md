## Selected architecture: one composed lifecycle execution
Fable revised the initial fully host-owned proposal. The supported candidate composes existing start, qualify, open and serve bodies inside one functions.exec closure. Runtime code owns all stages, paths, raw-byte hashes, pinned loading, native tool calls, bounded recovery and state transitions. The model cannot select a stage or rewrite generated code in the normal path. This is deterministic internal orchestration, not a claim that the whole host lifecycle is model-free.

A minimal routing skill contains one constant bootstrap and three host-level rules: launch once, attempt one final response only when the running cell requests the genuine Stop probe, then functions.wait on that same cell while it remains live. The model does not choose a runtime stage, destination after setup, SHA, packet, direct node_repl call or fallback. If this residual contract is still unreliable in Luna trials, the candidate fails acceptance; do not silently substitute Terra High.

Implementation prerequisite P0a is a bounded reproduction, not a speculative new platform feature: demonstrate that one functions.exec closure calls the existing native tools, survives yields, observes a genuine Stop event from an interleaved final attempt, and resumes that same closure. Use disposable state, no canonical owner changes or worker sends. Code supports this hypothesis but current-host behavior is not proved. Record exact host build and real executor/Stop trace. P0a failure stops rollout and requires a concrete host or code diagnosis.

Fully eliminating the model-level final and wait calls would require supported host lifecycle controls not established here. That is a recorded platform limitation, not a prerequisite to implementing and testing this smaller candidate. Do not claim those controls exist or bypass trust to simulate them.

## Public contract and execution protocol
Normal start input is empty: {}. Runtime reads the previously enrolled exact worker IDs from canonical configuration. No worker overrides in the constant bootstrap. New user-requested destinations use the existing separate configuration/replacement flow before this operation; name ambiguity is resolved there, not injected into code. Missing configuration yields blocked/pool_not_configured before acquisition. No caller-provided task identity, stage, execution source, proof or force flag.
Operation status: {operation_id, state: starting|qualifying|ready|blocked|failed|stopped, reason, session_directory|null, generation|null, capacity, admission_observed, observed_at, evidence_path}. Ready requires a currently observed bound admission waiter. A historical ready result is not a promise after host loss. The execution transport is existing functions.exec/functions.wait. This is not a newly invented MCP tool. Add a single lifecycle packet stage to the installed helper; preserve older packet formats only for explicit diagnostics and compatibility.

Runtime rules:
- Serialize duplicate starts under existing authority lock; reobserve current healthy service and return it without another sender or generation bump.
- Same-operation retries inspect canonical outcome. Never resend or replay consumed serve after a lost acknowledgment. Existing stale/commit_unknown bounded recovery remains authoritative.
- Preflight capability before acquiring owner. Trusted disk configuration does not prove the active desktop has loaded it.
- Do not acquire readiness before genuine qualification. Failure preserves diagnostic and leaves admission closed.
- Once acquired and qualified, open and start original serve exactly once. Runtime retains handle and renews liveness through existing authenticated path only.
- Original execution loss closes admission using existing detector; preserve accepted request recovery and uncertain delivery. Do not retry a send with uncertain outcome.
- Different worker pool uses existing idle/exclusion policy. Do not clear old receipts, busy work or stale authority to make tests pass.
- Missing/modified hook reports actual source and verified CLI approval route. Approval once is a platform requirement, not a routine start question. Never rewrite trust hashes. If trusted qualification fails, classify execution/host fault instead of asking trust again.
- No automatic app restart, worker-message probe, migration-code deletion or platform-security change as part of startup.

## Implementation record (2026-09-27, pending review)
- Normal path: listener-start.md carries one constant, input-free functions.exec bootstrap. It runs `listener start` from the selected installation (revision 2 below) and evaluates the returned packet-call loader. Hook preflight ties that helper to the host-trusted hook (a different checkout or plugin copy is `wrong_definition`). No usable selection reports blocked, never a guessed path.
- `listener start` with no worker flags reads the enrolled pool; none yields blocked/pool_not_configured before acquisition. `--worker-1/--worker-2` remains the explicit destination flow and returns the same composed loader. It writes lifecycle.json privately and returns a readResidentPacketCall loader for the new `lifecycle` stage; the older `listener-start-packet` stays for diagnostics and compatibility.
- The lifecycle closure runs capture, worker reads, and the guarded commit. commit_unknown re-inspects the same operation once; stale regenerates once from canonical state for the same destinations, never with physical evidence. It then evaluates the pinned qualify, open, and serve stage loaders produced inside the REPL. Events: schema_version 1, kind listener_lifecycle, operation_id, state (starting|qualifying|ready|blocked|failed|stopped), action (wait|finalize|stop). Receipts go to the private operation directory with native task/turn, installed revision, and host build.
- Qualification: prepare writes the challenge, registers the watcher and 45 s deadline, and persists the armed receipt before action=finalize. Wait settles the same REPL-held promise. On the deadline the waiter links a terminal receipt (operation, task, turn, generation, owner, nonce; waiter closed; qualified and send_authorized false) into the observed slot. The hook links the challenge copy into the same slot. The single link arbitrates, so a late Stop cannot turn a timeout into success and a timeout cannot erase an earlier Stop.
- Hook: with a terminal receipt, a non-owner task is released by the existing rule. The owner task is released only when the receipt matches the current generation, owner, startup operation, and turn, the owner is unbound and fully idle, no assignment or claim is active, and three canonical rereads are unchanged. Anything else, including moved authority in the same task, blocks. The hook definition (hooks/hooks.json) is unchanged; script bytes and the activation pin changed.
- A second launch in a turn whose Stop probe already ran is refused before acquisition (probe_already_attempted_this_turn).
- Readiness: a separate read-only `resident-ready` process observes resident-status until a live waiter; only then is state=ready emitted, with action=wait.
- Revision 1 (Fable code review 1): the readiness observer is auxiliary. A refused or failed observer only yields state=starting, reason admission_not_observed, observer_error; it never emits ready and never ends the serve. Each observer process is drained with write_stdin until it exits, and the closure awaits it and the serve before any stop event; an unexpected closure error also awaits a started serve. Relayed serve outputs carry admission_observed=false. The timeout diagnostic no longer infers from an accepted final that the hook never ran, and names one recovery: a new Listener task. SKILL.md and native-activation.md route start, restart and replacement to listener-start.md; the multi-stage recipe is diagnostics-only. (Revision 1 also declared plugin-only installs unsupported for the listener; the coordinator rejected that narrowing, and revision 2 replaces it.)
- Revision 2 (coordinator decision, 2026-09-27): plugin installs keep resident startup, as compatibility.md and README already state. The constant bootstrap selects one installation by a fixed rule, in `/bin/sh` so the user's shell cannot change glob behavior: the source-install link `$HOME/.local/bin/pro-dispatch` whenever it exists, even if broken; otherwise the single `${CODEX_HOME:-$HOME/.codex}/plugins/cache/codex-pro-dispatch/codex-pro-dispatch/<version>/skills/codex-pro-dispatch/scripts/pro-dispatch`. The selected CLI's existing hook preflight then requires the host's single resident Stop hook to be that tree's own command, so a stale link or copy cannot pass against another installation's hook. Preflight now always reports `expected_command` and each hook's `source`, `pluginId` and `sourcePath`, and its missing/wrong-definition actions name both installation kinds. No new API, environment variable, runtime framework, trust write or model input; the runtime below the entry was already tree-relative. Bootstrap: 1188 bytes, sha256 048ad3f3…caa644.
